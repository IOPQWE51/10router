# Mirasim-bundled dsh tool_call id/name loss → 11133

> Investigated: 2026-09-01 · Verdict: **bug in mirasim's bundled dsh; 10Router does not work around it**

## Symptom

Inside **mirasim**, using its bundled **dsh** (DeepSeek Harness) to call DeepSeek-family models (`cbcn/deepseek-v4-pro` / `ds/deepseek-v4-pro`) fails after a few tool-calling turns:

- **codebuddy**: `400 code 11133` ("request parameters were rejected by the model provider")
- **official DeepSeek**: `400 "An assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'"`
- **dsh frontend**: `Error: unknown tool ""`

## Investigation

### Environment comparison (decisive)

| Environment | Result |
|-------------|--------|
| NAS standalone dsh (independent install) | ✅ works |
| mirasim + dsh | ❌ 11133 |
| mirasim + codex | ✅ works |
| Claude Code → 10Router | ✅ works |
| mirasim + dsh + official DeepSeek | ❌ 400 (tool_calls without tool responses) |

- NAS standalone dsh works → **10Router + codebuddy + official DeepSeek are all fine**
- mirasim + codex works → mirasim's own serialization is largely fine
- Claude Code works → 10Router translator builds tool_calls correctly
- **Only mirasim's bundled dsh fails**

### Capture evidence (10Router `DEBUG_RAW_REQ` diagnostic)

A mirasim+dsh pro request (27 tool_calls):

| tool_calls id source | count | note |
|----------------------|-------|------|
| `chatcmpl-tool-...` | 19 | **non-standard id format previously returned by codebuddy** |
| `call_00/call_01` | 2 | generated by dsh itself |
| **empty string `""`** | **6** | **ids lost when dsh replayed history** |

Also `function.name` was empty (`hasEmptyName=true`).

Control group hy4 request: tc=tr fully matched, no empty id, no empty name → **hy4 works**.

## Root cause

1. **codebuddy returns non-standard tool_calls ids** (`chatcmpl-tool-...`, not OpenAI-standard `call_...`)
2. **mirasim's bundled dsh stores codebuddy-returned tool_calls into session history**, then replays them across turns
3. **dsh mishandles codebuddy's `chatcmpl-tool-` ids**, losing some to empty `""` and also emptying `function.name` on replay
4. codebuddy / official DeepSeek reject tool_calls with empty id + empty name

## Verdict

**This is a bug in mirasim's bundled dsh handling of non-standard tool_calls ids** — not 10Router, codebuddy, or official DeepSeek:

- 10Router forwards verbatim (openai→openai); it cannot restore ids/names dsh already lost
- codebuddy / official DeepSeek correctly reject the malformed request

## Handling

**10Router does not work around it** — adapting to a third-party bug would introduce a dependency on non-standard formats. Recommendations:

1. **Short term**: use codex in mirasim, or NAS standalone dsh / Claude Code (all work)
2. **Report**: file the bug with the mirasim team about its bundled dsh's handling of codebuddy non-standard tool_calls ids

## Related

- 10Router already **drops empty `function.name`** in streaming passthrough (commit `48e39b44`) to help clients that parse correctly avoid `unknown tool ""` — but that fixes response-side forwarding, not the request-side ids/names mirasim+dsh already lost.
- The diagnostic code used (`DEBUG_RAW_REQ` / `DEBUG_CB_REQ`) has been removed from 10Router.
